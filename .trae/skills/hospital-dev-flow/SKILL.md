# 医院项目协作开发流程

用户的需求是逐步完善的，流程有歧义先问再动。当开始一个新模块（如"开始就诊人模块"）时，严格执行以下五步。

## 五步流程

### ① 设计问答（写代码前）
- **先问后写**：VO 该有哪些字段、前端传什么、后端返什么、删前查哪些表、校验放哪层
- **单题出题**：一次只抛一题，用户答完、讲评完再出下一题；不一次性铺开多题（初学者串着答会乱）
- 问前端需求："管理端页面要展示/提交哪些字段？患者端列表需要什么？"
- 用户答错不要直接甩答案，先纠偏并讲理由（是什么 → 为什么 → 不这么做会怎样）
- 设计分歧点（如字段可否为 NULL）明确问用户"你看是改还是留着"，权衡后给结论

### ② 确认生成
- 问题答完，问用户"可以生成了吗"，用户说"生成"才动手写代码
- 生成顺序：DTO → VO → Service 接口 → ServiceImpl → Controller
- 写完跑 `mvn -q -f hospital-service/pom.xml test` 验证编译，报告退出码

### ③ 读源码
- 给文件清单 + 阅读顺序（按数据流：DTO → VO → Service → Impl → Controller），标出重点文件
- 不催促；等用户说"看完源码了"才进入下一步
- **禁止在用户读码之前考代码细节**——那时考核信号是脏的

### ④ 代码考核（只考差异点）
- **只根据真实代码提问**，可指向具体文件和方法；不重复考已掌握的通用内容
- 答题格式：「是什么 → 为什么 → 不这么做会怎样」
- 答错的点记入 `心得.md` 的"未解决问题"区块，后续模块回头补，不许悄悄溜走
- 考核全部通过后才给测试用例

### ⑤ 测试
- 给 Knife4j 用例清单：正常流 + 边界 + 权限各至少一条，每条写明预期 code/msg
- 用户自测（`http://localhost:8080/doc.html`，先登录拿 token，Authorize 填 `Bearer token`）
- 用户报结果；失败贴响应原文，再排查

## 固定规范

- **DTO/VO**（黑马规范）：入参 `dto/xxx/XxxCreateDTO`、`XxxUpdateDTO`；出参 `vo/xxx/XxxVO` 含 `from(Entity)` 静态转换
- **VO 原则**：信息最小化（前端不要的不给），但列表 VO 永远带 id；权限、钱相关字段由服务端决定，不收客户端默认值
- **笔记分工**：`心得.md` 只记知识点；`改进记录.md` 记「现象 → 根因 → 修复 → 通用教训」
- **排障收尾必问**（2026-11-27 定）：任何一次"用户提出问题 → 定位 → 解决"的排障或答疑结束、确认问题已解决后，**主动问一句"要不要记到心得.md"**。不擅自写入，但必须问；用户说记就按下方模板写，说不用就跳过。这是提醒机制，不是自动落笔。
- **每模块完成**：更新两份笔记 + git commit & push（等用户确认推送成功）
- `application.yml` 的 `hospital.jwt.expire-hours` 开发期为 720，M5 部署前必须改回 2
- Report 实体和 ReportMapper 已建（M3 报告模块用），`DoctorServiceImpl.delete()` 已查 tb_schedule + tb_report 两张引用表
- **前端由助手生成**（2026-11-09 定）：患者端 + 管理端用 Vue3 + Element Plus + axios，等后端 M4 末/M5 初 API 稳定后一次性生成，用户零前端工作量、只验收；面试定位为"后端深度 + 脚手架前端"
- **八股现场补**：开发中遇到八股高频技术点（Redis 分布式锁、MySQL 行锁与索引、事务隔离级别、连接池等），先用一小节讲清"是什么 → 为什么 → 面试官怎么问"，再进入代码；讲完织入当天笔记
- **新增前端页面**：路由注册 + 侧边栏入口必须可点（不留灰色占位，空菜单比没菜单更伤）+ vitest 用例至少覆盖「渲染 / 空状态 / 失败重试」
- **改状态机**：枚举 → 条件 UPDATE 迁移（`WHERE status=旧值` 查影响行数）→ 前端按钮可见性 → 集成测试 → README 状态说明，五处一起改，缺一处就出现"页面能点但接口拒"
- **改行为同步文档**：功能清单、演示账号表、就医闭环图、测试数量都要跟着改；README 里的数字（用例数、测试类数）最容易过期，改完测试顺手核对一遍

## 环境与命令约定

**分工**：命令类操作（`mvn` / `docker` / `npm` / `k6` / 建目录）由**用户自己执行**；助手负责写代码、讲原理、给验证清单和预期输出。助手不要替用户跑构建、起容器、压测（只读查询和诊断命令可以跑）。

**验证三件套**（每次改动后按需跑，失败就把完整堆栈给用户看）：

- 后端：`cd hospital-service` → `mvn test`（10 个集成测试，**连真实 MySQL + Redis，不 mock**，Docker 必须起着）
- 前端类型：`cd hospital-web` → `npx vue-tsc --noEmit`
- 前端测试：`npm test`（vitest，327 个用例）

**端口与环境**：本地开发由 `application.yml` 的 `spring.config.import` 自动读取根目录 `.env`（MySQL `3307`、Redis `6380`，注意不是 3306/6379）；Docker 容器内走服务名，CI 没有 `.env` 时回落到 3306/6379。改代码后必须 `docker compose up -d --build app|web`——**镜像不可变，`up -d` 不重建**。只改数据或 `.env`/`application.yml` 时不需要重建。

**接口存在性**：判断某接口是否已部署，查 `http://localhost:8080/v3/api-docs`；不要用 401/404 判断——Spring Security 在路由前就返回 401。

**演示数据**：`admin` / `doctor001`~`doctor005` / `admin123`；患者账号自行注册（注册后先添加就诊人才可挂号）。`perf001`~`perf500` 与排班 `9001` 只给压测用，不要拿来演示；演示前确认排班 `work_date` 未过期，否则患者端显示无可约号。

**数据脚本**：`sql/data.sql` 只在数据卷**首次初始化**时执行，之后改动不会自动生效——需要另写补丁 SQL 直接执行（`Get-Content x.sql | docker exec -i hospital-mysql mysql -uroot -p123456`）。含 `$` 的 SQL 不要用 `mysql -e "..."` 拼，PowerShell 会把哈希里的 `$xxx` 当变量吞掉。

**git**：用户明确说“提交/推送”才执行；推送要带代理（本机 Clash 在 7897，git 不读系统代理）：

```powershell
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push origin main
```

## 排障收尾：问一句，写一段

排障（报错、接口 404、环境不一致、数据对不上、行为不符合预期）结束后，先给结论，再问一句"这条要不要记到心得.md"。

- 记**心得.md**：通用机制与排查方法（如"容器是新的、镜像是旧的"、401 ≠ 接口存在、怎么用 `/v3/api-docs` 验证路由）。写成"现象 → 原理 → 排查三步 → 规则表 → 面试一句话"，脱离本项目也成立。
- 记**改进记录.md**：项目内的具体缺陷与修复（现象 → 根因 → 修复 → 验证 → 教训），带文件路径和错误码。
- 同一次排障两边都可以记：心得讲机制，改进记录讲这次踩的坑。
- 问题还没确认解决时**不要问**，否则会记下错误结论。

## 面试准备（M5 阶段激活）

素材入口：`docs/design-doc.md`（架构设计）、`改进记录.md`（踩坑排查，逐条展开成"现象→定位→方案→权衡"的面试话术）、`心得.md`（设计理解）。用户说开始准备面试时，从改进记录逐条陪练口述。

**M5 含系统优化环节**：压测后按清单逐项优化——慢 SQL 与 EXPLAIN、索引命中、连接池参数（maximum-pool-size 等）、Redis 内存与过期策略、JVM 参数；每个优化点记入《改进记录.md》，格式同「现象 → 根因 → 修复 → 效果对比」。
