# 面试问答预演

> 结构：问题 → 一句话结论 → 展开（结合本项目真实实现）→ 可能的追问。
> 回答原则：先给结论，再用一个具体机制或数字支撑，最后补一句取舍。

---

## 一、架构与选型

### Q1 介绍一下这个项目

**结论**：一个前后端分离的医院挂号系统，覆盖患者、医生、管理员三种角色，核心是"挂号秒杀 + 就诊状态机 + AI 导诊"三条链路。

**展开**：
- 技术栈：Spring Boot 3 + MyBatis-Plus + MySQL + Redis；Vue 3 + TypeScript + Vite + Element Plus；Spring AI 接大模型
- 业务闭环：注册 → 添加就诊人 → 选排班挂号 → 支付 → 签到 → 医生叫号（就诊中）→ 完成接诊 → 查报告
- 工程化：Docker Compose 一键起服务、多阶段构建、GitHub Actions CI、k6 压测、后端 16 个集成测试 + 前端 331 个单测

**追问：为什么不用微服务？**
单体 + 单库能覆盖当前量级，拆微服务会立刻引入分布式事务、服务发现、链路追踪的复杂度，收益不匹配。架构是演进出来的，不是一开始就设计成终态。

### Q2 为什么选 MyBatis-Plus 而不是 JPA

**结论**：挂号场景的 SQL 是"条件更新 + 唯一键冲突"这类精细控制，需要能直写 SQL。

**展开**：扣库存是 `UPDATE ... SET left_num = left_num - 1 WHERE id = ? AND left_num > 0`，还要接唯一键冲突做幂等判断。JPA 的脏检查抽象反而挡路，MyBatis-Plus 保留了手写 SQL 的能力，又省掉单表 CRUD。

### Q3 前后端怎么分工鉴权

**结论**：JWT 无状态，后端从 token 解出 userId/role，接口一律不信任前端传的身份字段。

**展开**：下单接口 `OrderCreateDTO` 只有 `scheduleId` 和 `patientId`，**没有 userId**——如果让前端传，改个参数就能替别人下单。就诊人还要校验归属：`patient.userId == token.userId`。管理端 `/admin/**` 在 Security 配置里限定 role。

## 二、并发与数据一致性（重点）

### Q4 两个人同时抢最后一个号，怎么保证不超卖

**结论**：三道防线，Redis 削峰、数据库条件更新兜底、唯一键防重。

**展开**：
1. Redis 用 Lua 脚本原子扣减 `stock:{scheduleId}`，`SETNX` 懒加载回填，避免 GET 再 SET 的竞态
2. 真正扣号是数据库条件 UPDATE：`WHERE left_num > 0`，影响行数为 0 就说明没了
3. 一人一单靠 `uk_patient_schedule(patient_id, schedule_id, active_flag)`，退号时把 `active_flag` 置 NULL 让出唯一键

测试验证：15 个线程抢 5 个号，恰好 5 单成功，库存归零，锁定号源数 = 5。

**追问：Redis 挂了怎么办？**
降级直连数据库。Lua 抛异常时捕获 `DataAccessException` 记日志继续走 DB，条件 UPDATE 自己能防超卖。Redis 只是削峰，不是正确性依赖。

### Q5 为什么要 active_flag 这种写法

**结论**：为了在"唯一键防重"和"退号后可重挂"之间同时成立。

**展开**：直接对 `(patient_id, schedule_id)` 建唯一键，退号后历史单还在，用户永远挂不上第二次。把 `active_flag` 设为 1 表示有效单、NULL 表示已释放，MySQL 唯一索引允许多个 NULL，于是历史单可以无限累积，有效单始终最多一条。

**追问：为什么不用软删除字段 `deleted`？**
`deleted` 通常是 0/1，退号置 1 后第二张退号单也置 1，还是会冲突。必须用 NULL 才符合唯一索引的语义。

### Q6 下单幂等是怎么做的，和唯一键有什么区别

**结论**：唯一键保证"数据不重复"，幂等保证"请求只生效一次"，两者解决不同问题。

**展开**：用户网络超时后重试，可能已经换了就诊人或排班——这时唯一键根本挡不住，会生成两张合法但用户不想要的单。
- 前端每次下单生成 `requestId`，失败重试复用
- 后端 `SETNX idempotent:order:{userId}:{requestId}`，值先写 `PENDING`
- 重复请求：`PENDING` 就返回"处理中"，已有订单号就直接返回原单
- **事务提交后**才把订单号写回 key，否则并发重试会读到未提交的订单
- 业务失败立刻删除占位，让用户能用同一个 requestId 重试

**追问：为什么不在事务提交前回写？**
会读到"有订单号但订单还不可见"的假阴性，触发删除 key，第三次重试又下一单。用 `TransactionSynchronization.afterCommit` 解决。

### Q7 分布式锁为什么只给定时任务用

**结论**：下单链路有唯一键兜底，定时任务没有"用户请求"这条天然串行线，多实例必然重复触发。

**展开**：`OrderTimeoutTask` 每 60 秒扫超时单，两个实例会同时扫同一批。加了 60 行的 `DistributedLock`：`SETNX + TTL` 抢占，释放时用 Lua 比对 token 再删，避免误删别人的锁。

**追问：Redis 挂了，锁失效，会怎样？**
降级为直接执行。重复执行是幂等的（条件 UPDATE），漏执行才会导致订单永远不释放。降级方向必须偏向"多跑"。

**追问：为什么不用 Redisson？**
只需要"抢一次、不等待、TTL 兜底"这三个能力，Redisson 的看门狗、可重入、公平锁都用不上，多一个重依赖不划算。

### Q8 支付和超时释放同时发生会怎样

**结论**：条件 UPDATE 保证只有一个赢，另一个影响 0 行直接放弃。

**展开**：支付是 `UPDATE tb_order SET status=1 WHERE id=? AND status=0`；超时释放是 `UPDATE ... SET status=4 WHERE id=? AND status=0`。两个 SQL 只有一方成功。测试里并发跑了 5 轮，断言终态互斥（已支付 XOR 已取消），且号源、库存、支付单三方数据一致。

## 三、状态机与业务闭环

### Q9 订单状态机是怎么设计的

**结论**：0 待支付 → 1 已支付 → 6 就诊中 → 3 已就诊；旁路是 2 已退号、4 已取消、5 已爽约。

**展开**：每次状态流转都写条件 UPDATE，非法流转影响 0 行。叫号是 1→6，完成接诊是 6→3，退号只允许 0/1，开报告要求 6 或 3。

**追问：刷新页面后"就诊中"丢了怎么办？**
这是实际踩过的 bug。前端只接受 `status===3` 恢复缓存，叫号后刷新就清空。修法是后端提供 `GET /doctor-work/current`，前端无缓存时从服务端查当前接诊患者。

### Q10 夜间收尾任务做什么

**结论**：每天 22:00 把当天时段已结束、还停在已支付/就诊中的订单推到终态。

**展开**：分流只看 `sign_time`——签到了但没叫完算已就诊，没签到算爽约。就诊中的单也必须收尾，否则会永久卡在状态 6。号源和库存不动，时段已过没有回补意义。

### Q11 为什么订单要存患者姓名快照

**结论**：医疗单据是法律文书级数据，不能因为患者改名就让历史记录跟着变。

**展开**：原来订单详情实时 join 就诊人表，患者改个名字，去年的单据也变了。现在下单时把 `patient_name` 写进订单，展示优先用快照，没有快照才 fallback 查表。历史数据用一条 JOIN UPDATE 回填。

## 四、AI 能力

### Q12 AI 导诊是怎么实现的

**结论**：Spring AI 的 Function Calling Agent，暴露 4 个工具，模型自己决定查什么。

**展开**：工具是查科室、查医生、查最近 7 天可约号源、查就医知识库。模型根据症状决定调用链，比如"咳嗽一周"→ 查呼吸内科 → 查医生 → 查号源。因为查的是库里真实数据，不需要像单轮问答那样"回库校验模型有没有编科室名"。

**追问：模型胡编怎么办？**
科室和号源都来自工具返回，模型只负责组织语言。另外 system prompt 约束它不做诊断、只做分诊，危险症状（胸痛、呼吸困难）直接提醒就医。

### Q13 SSE 流式怎么做的

**结论**：`ChatClient.stream()` 返回 `Flux<String>`，`SseEmitter` 桥接成 SSE；流末尾用 `[SCHEDULES]` 前缀追加结构化号源。

**展开**：一条通道传两种数据——纯文本直接推，号源 JSON 带前缀，前端按前缀分流。文本流结束后 `concatWith(Flux.defer(...))` 才读取工具暂存的号源，保证顺序。前端用 `fetch + ReadableStream` 接收（EventSource 只支持 GET，这里是 POST）。

**追问：为什么不用 WebSocket？**
单向推送、请求-响应式，SSE 够用且是纯 HTTP，不用处理粘性会话和心跳。

### Q14 会话记忆怎么存的

**结论**：Redis List，`rightPush` 追加、`trim` 只留最近 10 轮、`expire` 2 小时。

**展开**：消息格式就是 `{"role":"user","content":"..."}`。读取失败按无历史处理，不影响主流程——记忆是锦上添花。

**追问：为什么不用向量库存记忆？**
10 轮的对话量用 List 足够，语义检索是另一个问题（长期记忆）。先解决"有没有上下文"，再谈"检索准不准"。

### Q15 RAG 做到了什么程度

**结论**：简化版，内置 6 条就医知识（挂号流程、退号规则、医保、报告、签到、科室），关键词匹配返回标准答案。

**展开**：知识条目少、关键词明确时，`Map + contains` 比向量检索更简单可控。升级路径写在设计文档里：文档切片 → Embedding → Redis 向量检索 → LLM 生成。

**追问：这和"真 RAG"差在哪？**
差在召回。关键词匹配对同义表达无能为力（"怎么取消挂号"匹配不到"退号"），向量检索能解决；代价是要维护 embedding 和索引。当前知识库只有 6 条，不值得。

## 五、工程化与部署

### Q16 为什么 Dockerfile 要改成多阶段构建

**结论**：原来的 Dockerfile 只 `COPY target/*.jar`，`--build` 根本没编译代码，容器跑的还是旧包。

**展开**：改成分两个 stage：`maven:3.9-eclipse-temurin-17` 里先 `dependency:resolve` 单独一层（改代码不用重下依赖），再 `COPY src` 打包；运行阶段只留 JRE。配 `.dockerignore` 排除 target。

**教训一句话**：镜像不可变，"容器是新的"不等于"代码是新的"。

### Q17 本地开发和容器端口怎么对齐

**结论**：容器内 MySQL 3306、Redis 6379，宿主机映射 3307/6380，靠 `.env` 和 `spring.config.import` 对齐。

**展开**：`application.yml` 里 `spring.config.import: optional:file:.env`，本地启动自动读 `.env` 的 `MYSQL_PORT=3307`。容器内服务之间用服务名直连 3306，不受影响。

### Q18 测试怎么保证改了核心逻辑不翻车

**结论**：后端集成测试打真实 MySQL/Redis，前端单测到组件交互层。

**展开**：`OrderConcurrencyTest` 用 `CountDownLatch` 真的并发 15 个线程抢号，断言库存和订单数；`DistributedLockTest` 两个线程验证互斥和复用；`AuthFlowTest` 验证注册后不自动建就诊人。前端 331 条测试覆盖组件渲染、表单校验、API 调用参数。

**追问：测试通过就代表没问题吗？**
不代表。上一轮就出现过"测试全绿但刷新丢状态"的问题——测试没覆盖刷新恢复场景。所以每次修 bug 都补一条回归测试。

## 六、反思类

### Q19 这个项目最大的技术债是什么

**结论**：历史就诊人"姓名=手机号"，以及演示数据与真实业务约束的冲突。

**展开**：早期注册会自动建一个"姓名=手机号"的就诊人，导致医生端显示手机号。修复方式是启动时把这类记录标成"待完善"，前端提示用户改——因为无法替用户编真实姓名。另外身份证最初选填，500 个压测就诊人没有证件号，强制必填前必须先把数据补齐。

**想表达的**：技术债不可怕，可怕的是没有还债路径。标记 + 引导修改，比"假装数据是对的"更诚实。

### Q20 如果再给你两周，你做什么

**结论**：优先做"能被验证的可靠性"，而不是堆功能。

**展开**：
1. 订单状态流转的审计日志（谁在什么时候改了什么状态）
2. 通知外发（短信/微信），现在只有站内信
3. 前端 E2E 冒烟（Playwright 已接入，补关键链路）
4. 压测报告进 CI，防止性能回归

**不做的**：微服务拆分、异步下单、向量 RAG——当前量级用不上，属于过度设计。

## 七、性能与压测

### Q21 你做过压测吗，数据怎么样

**结论**：做过，读接口 2950 req/s，写链路约 19 单/秒，瓶颈定位在库存行锁。

**展开**（本地 Docker 单机，MySQL / Redis / 应用同机）：

| 场景 | 并发 | 吞吐 | p95 |
|---|---|---|---|
| 号源查询 | 100 VU | 2950 req/s | 77 ms |
| 挂号闭环（5 排班分散） | 100 VU | 19 单/s（HTTP 63 req/s） | 1.23 s |
| 挂号闭环（单排班热点） | 50 VU | 7 单/s | 1.82 s |

挂号闭环口径是"下单 → 支付 → 退号"，单位是完整成单/秒。

**追问：为什么写这么慢？**
不是代码慢，是 `tb_schedule.left_num` 单行锁：同一排班的所有写操作串行排队。把压测分散到 5 个排班后吞吐从 7 涨到 19、p95 降 32%，直接证明瓶颈在行锁。生产优化方向是库存分桶或按医生拆表，不是加机器。

### Q22 压测中发现过什么问题

**结论**：发现一个死锁，而且它会连锁成用户可见的故障。

**展开**：压 50 并发闭环时，部分用户突然永久无法挂号。查库发现订单卡在"已支付"，占着唯一键。日志是 `Deadlock found`。

根因是两条路径加锁顺序相反：
- 下单：`schedule` → `number_source` → `order`
- 退号：`order` → `number_source` → `schedule`

A 持 schedule 等 source，B 持 source 等 schedule，成环。退号被回滚 → 订单停在已支付 → 唯一键不释放 → 该就诊人再也不能挂这个排班。

修法是把退号顺序改成和下单一致，订单状态的条件 UPDATE 放到最后，失败靠回滚兜底。

**想表达的**：死锁不是玄学，是加锁顺序成环的必然结果；单压一个接口测不出来，必须跑完整闭环。

## 附：三个"一句话亮点"（自我介绍时用）

1. **挂号链路三道防线**：Redis Lua 削峰 + 数据库条件更新兜底 + 唯一键防重，15 并发抢 5 号只成功 5 单。
2. **请求级幂等**：`requestId` + Redis 占位 + 事务提交后回写，解决唯一键挡不住的"重试重复下单"。
3. **AI 是 Agent 不是问答**：4 个工具 + 自己决定调用链 + SSE 流式 + 会话记忆，查的是库里的真实号源。
